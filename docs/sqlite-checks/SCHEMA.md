# SCHEMA: loading sqlite_schema rows into schema objects

Area key: SCHEMA. Sources: SQLite 3.53.4 split amalgamation (`prepare.c`, `build.c`, `trigger.c`, `vtab.c`, `callback.c`, `analyze.c`, `parse.c`/`parse.y`, `util.c`, `btree.c`). Our code: `src/MBW.Utilities.ManagedSqlite/Core` and `src/MBW.Utilities.ManagedSqlite/Sql` at commit `debcfb3`.

**How the results were checked.** Every row marked "verified" was reproduced in two steps. First, a test database was built with Python's `sqlite3` module (SQLite 3.45.1), and its `sqlite_master` was edited under `PRAGMA writable_schema=ON` or its header bytes were patched. Second, it was opened on a fresh connection, which ran `SELECT count(*) FROM sqlite_master` (this loads the schema) and then a `SELECT` from the target table. The same file was then run through our library (`Sqlite3Database` → `GetTable` → `EnumerateRows` → `GetTableDefinition`). The scripts and generated databases are in `review/sqlite-checks/repro/schema/` (`t.py`, `t2.py`, `t3.py`, `db_*.db`). The .NET harness is a copy of the repo under `.../scratchpad/repo/src/Harness`. The repo itself was not modified.

## 1. Overview

SQLite does not read the schema at `sqlite3_open`. The first statement that needs it calls `sqlite3ReadSchema` → `sqlite3Init` → `sqlite3InitOne` (prepare.c), and the steps below follow from there:

- **Header fields.** It sets `db->init.busy=1`, starts a read transaction and reads the header meta values. The text encoding is masked with `&3` and 0 means UTF-8. A schema format number above 4 is refused with "unsupported file format". The schema cookie and cache size are taken as they are.
- **Row loading.** It runs `SELECT*FROM "main".sqlite_master ORDER BY rowid` through `sqlite3_exec`. Each row reaches `sqlite3InitCallback` as five **C strings** (`sqlite3_column_text`): integers and blobs become text, and text stops at the first NUL.
- **Rows with SQL.** If `sql` starts with the two bytes `cr` (case-insensitive, with no whitespace or comment skipping), the callback stores the rootpage in `db->init.newTnum` and runs the full SQL parser on the statement with `init.busy` set. `sqlite3StartTable`/`sqlite3EndTable`, `sqlite3CreateIndex`, `sqlite3BeginTrigger`/`sqlite3FinishTrigger`, `sqlite3CreateView` and `sqlite3VtabBeginParse`/`sqlite3VtabFinishParse` then build the in-memory objects without emitting VDBE code. During this parse SQLite checks:
  - that type/name/tbl_name match the SQL (`sqlite3CheckObjectName`);
  - for name collisions;
  - every semantic rule of CREATE TABLE, CREATE INDEX and CREATE TRIGGER;
  - that the rootpage is a well-formed unsigned integer no larger than the page count.
- **Rows with a NULL or empty `sql`.** These must name an automatic index that an earlier CREATE TABLE already created ("orphan index"), with a rootpage in `2..mxPage` that no sibling index shares.
- **How errors are reported.** Any error becomes `corruptSchema()` → "malformed database schema (name) - detail" / `SQLITE_CORRUPT`, and **the whole schema, and so the whole database, is unusable**. Only `PRAGMA writable_schema=ON` (`SQLITE_WriteSchema|SQLITE_NoSchemaError`) relaxes this. It skips the name/type checks and keeps whatever was loaded before the error.
- **Left until use:**
  - views and trigger bodies are not resolved;
  - virtual-table modules are not looked up;
  - unknown functions and collations are accepted;
  - a missing automatic index, or a table with rootpage 0, is caught only when a cursor is opened on it;
  - `sqlite_stat1` problems are ignored.

Our library reads every `sqlite_master` row into an `Sqlite3SchemaRow` with **no validation at all**. A row is only checked when its table is opened: root page bounds via `ReaderBase.SeekPage`, the b-tree kind against WITHOUT ROWID in the Sql package, and the SQL when `GetTableDefinition` parses it. Indexes, views and triggers are never checked.

## 3. Most important gaps

**SQLite rejects these and we accept them**

1. **No whole-schema validation.** SQLite refuses the entire database if any schema row is bad: a type/name/tbl_name mismatch (26), duplicate names (32-37), an orphan index (14), a bad CREATE INDEX, TRIGGER or VIEW (55-65), any CREATE parse or semantic error (38-51), a NULL rootpage on any row (11), or rows out of order (7). We check only the table that is opened, and indexes, views and triggers never. A Strict mode that matches SQLite needs an eager (or first-use) pass over the schema. A Lenient mode can skip that pass, which is what SQLite's own writable_schema does.
2. **Schema format number > 4 is not refused** (02). SQLite reports "unsupported file format".
3. **Table rootpage 1** (19): we return sqlite_master's rows as the user table's data. **Rootpage > 2^32 wraps** with `(uint)` and a REAL rootpage is rounded (17), so we can silently read the wrong b-tree.
4. **A virtual table with a non-zero rootpage** is read as an ordinary b-tree (58). The vtab test is also stricter than SQLite's parse about the exact text.
5. **Leading whitespace or a comment before `CREATE`** is accepted (13); SQLite reports malformed.
6. CREATE TABLE semantics we never check: multiple PKs, STRICT types, unknown table options (`FOOBAR`), more than 2000 columns, AUTOINCREMENT misuse, WITHOUT ROWID with no PK, CHECK/FK errors (40-49).
7. When we do reject SQL, `GetTableDefinition` throws `InvalidOperationException`, not `SqliteCorruptException` (22).

**We reject these and SQLite accepts them**

1. **Text encoding values other than 1..3** (0, 4, 5, 0x101, …): SQLite uses `&3`, and 0 means UTF-8. We fail the whole open unless `FallbackEncoding` is set (01).
2. **BLOB values in type/name/sql/rootpage**: SQLite reads them as text, while we fail the whole open with an InvalidCastException wrapped as corruption (08).
3. **`type='TABLE'`** (any case other than lower-case): SQLite accepts it, but our `FindTable` cannot see the table (26).
4. **Stored SQL that SQLite's re-parse accepts but our parser does not**: `IF NOT EXISTS` (30), `TEMP` (29), trailing text after the first `;` (24), text after an embedded NUL (09). Each makes `GetTableDefinition` fail.
5. Minor: Unicode case folding in name lookup matches names that SQLite keeps distinct (31). This is looser, not stricter.
