# INTEG: checks done only by PRAGMA integrity_check / quick_check

Survey area for issue #58. SQLite 3.53.4. B = `https://github.com/sqlite/sqlite/blob/version-3.53.4/src/btree.c#L`, P = `https://github.com/sqlite/sqlite/blob/version-3.53.4/src/pragma.c#L`.
Links are written out in full in the table.

## 1. Overview

`PRAGMA integrity_check` and `quick_check` compile to one `OP_IntegrityCk` opcode ([vdbe.c:7263](https://github.com/sqlite/sqlite/blob/version-3.53.4/src/vdbe.c#L7263)), which calls `sqlite3BtreeIntegrityCheck` ([btree.c:11144](https://github.com/sqlite/sqlite/blob/version-3.53.4/src/btree.c#L11144)), followed by VDBE code that `pragma.c` generates for each table. The b-tree part is the same for both pragmas. It does four things. (a) It walks the freelist against the header count. (b) It calls `checkTreePage` on every root page: this re-runs `btreeInitPage` and also runs `btreeComputeFreeSpace`, which the read path never runs. It then checks cell offsets and extents, rowid order against the parent's divider keys, overflow chain length, equal leaf depth, and whether cells and freeblocks overlap or leave gaps, comparing the gaps against the header's fragment count. (c) It keeps a one-bit-per-page map of every page referenced, so it reports pages used twice and pages never used. (d) On autovacuum databases it checks every pointer-map entry and the "largest root page" header field. Errors become text rows. Nothing returns SQLITE_CORRUPT and nothing is clamped. The per-table VDBE part does the following. It reads the last column of every row, which forces the whole record header to be parsed. It checks NOT NULL, STRICT types, and non-STRICT affinity types (TEXT values in numeric columns, numbers in TEXT columns), and evaluates CHECK constraints. It compares each table's row count with each index's entry count. With full integrity_check only (quick_check skips these), it also checks WITHOUT ROWID primary-key order and cross-checks every index entry: missing entries, the rowid at end of record, collation values, and UNIQUE. The ordinary read path does almost none of this. It catches bad page numbers, bad page types, too many cells, cells running past the page end (only when the payload is touched), short overflow chains, depth over 20, empty child pages, and the pending-byte page. Everything else here is detected only by the pragma. So under the #58 policy those checks are **Optional**: Lenient-relaxable, or candidates for an opt-in "verify" mode. Strict parity does not require them, and the schema-level ones must stay tolerated on normal reads.

Cheapness legend used in Notes: **[cheap-enum]** = O(1) or nearly so per cell/page, with data we already hold during a single-table enumeration. **[per-page]** = adds work per page on a page that is already in memory. **[full-scan]** = needs every tree, the freelist and the schema (whole file).

## 3. Most important gaps

**SQLite rejects (on the normal read path), we accept:**
1. **INTEG-R1 empty child page / INTEG-R2 empty non-page-1 interior root.** SQLite gives CORRUPT in moveToChild and moveToRoot. We read on silently. Strict-required, and cheap to add in `BTreeTools.ParseChild`.
2. **INTEG-03 pending-byte page.** Any reference to the lock page (DBs > 1 GiB) gives CORRUPT in the pager. We read it as data. One compare in `SeekPage`/`ReadPage`.
3. **INTEG-05 MX_CELL.** SQLite's `nCell > (pageSize-8)/6` bound is tighter than our "pointer array fits" bound. (The page-area survey owns this.)

**Integrity-only (SQLite accepts on reads, so these are Optional / Lenient-or-verify candidates; none is done today):**
- Cheap during a single-table enumeration: rowid strictly increasing and within divider bounds (14), equal leaf depth (17), visited-page bitmap for DAG, cycle and overflow-loop detection (02, 15), overflow chain longer than needed (16), freeblock chain and free-space sanity (06-11), and the incremental-vacuum header flag (24). Per-page but moderate: cell/freeblock overlap and fragmentation count (18, 19). Needs a full-file scan: never-used pages (29), cross-table double references (02), freelist checks (20-22), pointer map (25-28, 30), max-rootpage header (23).
- Schema-level checks (34-38: NOT NULL, STRICT types, affinity types, CHECK) must stay **tolerated** on normal reads. They fit only an explicit "verify" API, never default Strict.
- Index cross-checks (40-45) are N/A while indexes are not readable.

**We reject, SQLite accepts:**
1. **INTEG-12.** A cell pointer inside the header or pointer array is always rejected by us (we behave as `cell_size_check=ON`). Default SQLite does no such check and may read on. A Lenient candidate.
2. **INTEG-16 / INTEG-32 eager reads.** A short overflow chain, or a corrupt record-header tail, beyond the columns a query touches is tolerated by SQLite's lazy column reads. We reject the row because we decode the full payload and header. This matches `SELECT *` and integrity_check, so it is defensible for Strict, and a lazy-decode Lenient mode could relax it.
