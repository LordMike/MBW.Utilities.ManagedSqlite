# HDR: database file header and pager/database-level consistency

SQLite source: 3.53.4 (split amalgamation, line numbers from `/tmp/claude-0/sqlsrc/split`). I checked the behaviour marked "verified" by patching a real database and opening it read-only (`mode=ro`) with SQLite 3.45.1 (Python `sqlite3`). I ran the same files through our library with a scratch harness built from a copy of `src/` (the repo itself is unchanged). Test scripts: `review/sqlite-checks/repro/hdr/t.py`, `.../scratchpad/w.py` (WAL), `.../scratchpad/av.py` (ptrmap). Ours = `src/MBW.Utilities.ManagedSqlite/Core`.

## 1. Overview

SQLite reads the first 100 bytes once, in `sqlite3BtreeOpen`, through `sqlite3PagerReadFileheader`. This read zero-fills a short file. It is used only to choose the page size and reserved bytes; an invalid page size falls back to the default. The real validation happens in `lockBtree()` on the first read transaction:

1. It takes the page count from header offset 28, but only if that value is non-zero and the "version-valid-for" bytes (92..95) equal the change counter (24..27). Otherwise it uses ceil(file size / page size).
2. If that count is 0 (an empty file), every check is skipped and the file is treated as an empty database.
3. Otherwise it checks the magic string, the read version (≤2; 2 means WAL), and the payload fractions 64/32/32. It also checks the page size (a power of two, >256 and ≤65536, where the stored value 1 means 65536) and that the usable size is at least 480. All of these fail with SQLITE_NOTADB.
4. A valid in-header count that is larger than the file is SQLITE_CORRUPT. A write version above 2 only makes the database read-only.

The schema-layer meta values are read in `sqlite3InitOne` and are lenient:
- **Text encoding:** `meta & 3`, with 0 meaning UTF-8. It is never an error for the main database.
- **Schema format:** truncated to a byte, 0 means 1, and only a value above 4 fails, with "unsupported file format".
- **Freelist, schema cookie, cache size, user version, application id, SQLite version and the reserved-for-expansion bytes** are not validated on the read path; a few appear only in `integrity_check`.

The pager returns SQLITE_CORRUPT for page 0 and for the lock-byte page (the page holding byte 0x40000000), and zero-fills short reads. The b-tree layer rejects any page number above the header-derived page count.

Before reading, the pager also handles the side files:
- A hot rollback journal makes a read-only connection fail with SQLITE_READONLY_ROLLBACK.
- A `-wal` file, if one exists, is always opened, whatever the header says, and its committed frames override pages of the main file.

The reader reads both: `FromPath` opens a `-journal` and a `-wal` file next to the database, and `FromStreamWithJournal` and `FromStreamWithWal` take them as streams (see [WALJ.md](WALJ.md)).

## 3. Open gaps

**SQLite rejects, we accept:**
1. **Autovacuum ptrmap entry type (HDR-28).** SQLite fails a column read that skips whole overflow pages when the
   ptrmap entry it looks up has a type outside 1..5. The reader follows each overflow page's own next pointer and never
   reads the ptrmap, so it reads such a file.
