# WALJ: write-ahead log and rollback journal (read-only replay)

SQLite source: canonical `src/` of 3.53.4 (`/mnt/project-files/review/sqlite-src-3.53.4/`). Line numbers are those files' lines. Links use `https://github.com/sqlite/sqlite/blob/version-3.53.4/src/<file>#L<line>`.

Scope: the checks that a future read-only reader needs when it adds two features. The first reads committed frames from an optional `-wal` stream, emulating `walIndexRecover`, with no `-shm` and no locks. The second replays a hot rollback journal in memory to get a consistent snapshot. Today our library reads neither file. "Ours" is therefore "No (future WAL/journal work)" unless noted.

**Proposed API** says how future work should express each check through our check API:
- **Strict**: `Checks.Strict(ok, "WALJ-NN", $"...")` always fails.
- **Relaxable**: `Checks.Relaxable(ok, settings, "WALJ-NN", $"...")` fails in Strict mode. In Lenient mode it is reported and the given fallback is used.
- **Tolerate**: SQLite accepts the condition silently. We must do the same, never stricter. An optional diagnostic is fine, but it is not a failure.
- **N/A**: the check depends on locks, `-shm`, the file system, or write paths that a stream reader does not have. It is listed so that nobody looks for it again.

## 1. Overview

**WAL.** A `-wal` file is opened whenever it exists and the database file is non-empty, whatever header bytes 18/19 say. It is also opened when header byte 19 == 2 (`pagerOpenWalIfPresent`, `lockBtree`). Readers normally trust the wal-index header in `-shm`. When that header is missing, torn, or fails its checksum, a connection that can write runs `walIndexRecover`, which rebuilds the index from the `-wal` file alone, and this is what we will emulate:
- **Header.** It reads the 32-byte WAL header. A bad magic, a bad page size or a bad header checksum makes the **whole WAL be silently ignored**. A valid checksum with a version other than 3007000 is SQLITE_CANTOPEN.
- **Frames.** It then walks whole frames in order. Each frame must carry the header's salts, a non-zero page number, and a cumulative checksum that matches. The checksum is seeded by the header checksum, and bit 0 of the magic picks the byte order. The **first invalid frame ends the log**, silently.
- **Commits.** Only frames up to the last *commit frame* (`nTruncate != 0`) are visible. That commit frame's `nTruncate` becomes the database page count.
- **Reading a page.** A read looks up the newest frame ≤ mxFrame for the page and falls back to the main file. The WAL page count replaces the file-size page count, so `lockBtree` re-runs all header checks on page 1 as seen through the WAL.
- **Unreachable checks.** The rest of `wal.c` (shm header copies, read marks, `nBackfill`, retries, SQLITE_PROTOCOL, READONLY_RECOVERY/CANTINIT, hash-table CORRUPT) protects the shared-memory index and live concurrency. A lock-free reader that does its own recovery cannot reach these paths.

**Rollback journal.** On the first shared lock, before any WAL handling, `sqlite3PagerSharedLock` calls `hasHotJournal`. The journal is *hot* when all of these hold:
- `-journal` exists;
- no other process holds RESERVED;
- the database is non-empty;
- the first byte of the journal is non-zero.

A read-only connection then fails with SQLITE_READONLY_ROLLBACK. A read-write connection takes EXCLUSIVE and runs `pager_playback`:
- **Super-journal.** It reads the optional super-journal name from the journal's tail. If a valid name is present and that file does not exist, the journal is not hot and nothing is played back.
- **Headers and records.** It walks sector-aligned journal headers, each with magic, nRec, cksumInit and original size, and the first one also holds sector size and page size. Under each header it walks page records (pgno, page data, checksum).
- **Original size.** The database is truncated or extended to the original size from the first header.
- **Corruption.** Every kind of journal corruption simply *stops playback* (SQLITE_DONE or a short read), and what was already restored stays restored:
  - bad header magic;
  - invalid sector or page size;
  - pgno 0 or the lock-byte page;
  - checksum mismatch;
  - a truncated record.
- **Skipped records.** Records for pages above the original size are skipped.

None of this ever returns SQLITE_CORRUPT. The journal modes differ only in how a *finished* transaction neutralises the journal: DELETE removes it, TRUNCATE leaves 0 bytes, PERSIST and exclusive locking mode zero the header, MEMORY and OFF leave no file. That is why "first byte is non-zero" is the hotness test. After playback, `lockBtree` validates the restored page 1 with the normal HDR checks.

## 2. Checks

Reactions: CORRUPT = SQLITE_CORRUPT; CANTOPEN = SQLITE_CANTOPEN ("unable to open database file"); "ignore WAL" = WAL treated as empty (mxFrame = 0), with reads from the main file; "stop" = recovery or playback ends at that point with SQLITE_OK, keeping what was accepted before it. When: open = first read transaction (`sqlite3PagerSharedLock` / `lockBtree`, at schema load); page load = when a page is fetched.

## 3. Most important items for the future WAL/journal work

**Things SQLite rejects (must be Strict or Relaxable):**
1. **WAL version ≠ 3007000 with a valid header checksum (WALJ-11)** gives SQLITE_CANTOPEN. This is the only fatal WAL-file condition.
2. **Header checks on the effective page 1 (WALJ-25, WALJ-61)** and **header page count > WAL page count (WALJ-26)**. Validation must run on the WAL-overlaid or journal-replayed image, not on the raw main file.
3. **WAL page size ≠ DB page size (WALJ-28).** SQLite gives no clean read error, only CORRUPT on checkpoint or write. Proposed Relaxable, with Lenient ignoring the WAL.
4. **Super-journal existence (WALJ-45).** It decides whether playback happens at all, and a stream reader cannot decide it. Relaxable, with Lenient playing back; or take a caller callback.

**Things SQLite tolerates silently (we must not reject; list for tests):**
- Any bad WAL magic, page size or header checksum, and a WAL of 32 bytes or less: the WAL is ignored (WALJ-06..10).
- Frame salt mismatch, pgno 0 or checksum break: the log ends there. An uncommitted tail is invisible, and there is no resync (WALJ-14..18).
- Any journal corruption stops playback without error: bad magic, bad sector or page size, pgno 0, lock-byte page, checksum mismatch, short record. Out-of-range records are skipped without a checksum check (WALJ-46..59).
- The first-header truncation to the original size happens even if no record is valid (WALJ-54).

**Design decisions to record:**
- Hot journal on a read-only opener: SQLite returns READONLY_ROLLBACK, and we propose replay instead (WALJ-39).
- Assume no RESERVED lock (WALJ-35).
- Apply the journal first, then the WAL (WALJ-42).
- Use a 512-byte sector size for the first-header fit test (WALJ-46).
