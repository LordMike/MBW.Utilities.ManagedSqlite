# DDL: CREATE TABLE / INDEX / VIEW / TRIGGER / VIRTUAL TABLE as parsed from sqlite_schema

## 1. Overview

To load the schema, SQLite runs `SELECT * FROM sqlite_schema ORDER BY rowid` and passes each row to `sqlite3InitCallback` (prepare.c), with `db->init.busy=1`. The `type` column is not used to dispatch. If the `sql` text begins with the bytes `cr` (case-insensitive), SQLite runs the full parser on it (`sqlite3Prepare` → `sqlite3RunParser` → Lemon grammar from parse.y). The build.c, trigger.c and vtab.c action routines then build the in-memory objects, and no VDBE code is generated. While `init.busy` is set, a few checks are relaxed:
- TEMP is ignored.
- The `sqlite_` name reservation is skipped.
- Unknown functions and collations are allowed.
- Double-quoted strings are allowed.
- A trigger's table qualifier is dropped.
- An index may share a table's name.
- Variables in DEFAULT become NULL.

Other parts are deferred until the object is used: view bodies, trigger bodies and virtual-table modules. CHECK constraints are thrown away entirely when the b-tree is read-only.

Every other parse error and semantic error still fires, and `sqlite3CheckObjectName` additionally checks that `type`/`name`/`tbl_name` agree with the parsed statement. Any one such error goes to `corruptSchema()`, which sets `SQLITE_CORRUPT` with the message "malformed database schema (NAME) - MSG", and `sqlite3InitOne` then discards the whole schema. So one bad index, view, trigger or table makes every statement on the database fail. Only `PRAGMA writable_schema=ON` (`SQLITE_NoSchemaError`) gets past this. Parsing stops after the first complete statement, so text after its `;` is never tokenized.

Our side matches it. When the database is opened, every schema row's SQL (tables, indexes, views, triggers and virtual tables) is parsed by a port of SQLite's own parser (its Lemon tables, tokenizer and grammar actions) and checked as build.c checks it at init. A failure raises `SqliteCorruptException` with SQLite's message; in Lenient the Relaxable checks are reported instead.

Every row marked "verified" was run on real SQLite (3.45.1 through Python, with the rows written via `writable_schema`, opened both rw and ro) and on our parser through a harness at `review/sqlite-checks/repro/ddl/` (`cases.txt`, `cases2.txt`, `t.py`, `t3.py`, `H/`).

Legend for "Ours": `Sql/` = `src/MBW.Utilities.ManagedSqlite/Sql/`, `Core/` = `src/MBW.Utilities.ManagedSqlite/Core/`. "When" for SQLite is always *schema load*, which happens on the first prepare and makes the whole DB unusable, unless the row says *deferred*. The "When (ours)" column shows where our equivalent would sit (`table def` = `GetTableDefinition`).
