# PAGE: b-tree page-level consistency on the read path (btree.c)

Link base: `https://github.com/sqlite/sqlite/blob/version-3.53.4/src/btree.c#LN` (B = btree.c, P = pager.c, H = btreeInt.h). Our code: `src/MBW.Utilities.ManagedSqlite/Core/...` (abbreviated `Core/`).

## 1. Overview

SQLite validates a b-tree page lazily and cheaply when it is first brought into a cursor: `getAndInitPage()` rejects a page number above `btreePagecount()` (and the pager rejects page 0), then `btreeInitPage()` runs `decodeFlags()` (only type bytes 2, 5, 10, 13 are legal), sets the header offset (100 on page 1, else 0) and rejects `nCell > MX_CELL = (pageSize-8)/6`. That is all, by default. The heavier per-page checks (`btreeComputeFreeSpace()`: freeblock chain order/bounds/size, fragmented bytes, cell-content-area start; `btreeCellSizeCheck()`: each cell pointer inside `[iCellFirst, usableSize-4]` and each cell ending inside the usable area) run only on the write path, in `PRAGMA integrity_check`, or (cell sizes) when `PRAGMA cell_size_check=ON` / `SQLITE_ENABLE_OVERSIZE_CELL_CHECK` is set; otherwise `findCell()` simply masks the 16-bit offset with `pageSize-1` and reads whatever is there. The cursor layer adds structural checks: `btreeCursor()` rejects root page < 1 (and treats root 1 of a 0-page file as an empty table); `moveToRoot()` rejects a root whose intKey flag disagrees with the cursor kind (table cursor vs index/WITHOUT ROWID cursor) and an interior root with 0 cells unless it is page 1 (whose right child is then used); `moveToChild()` (and its inlined copy in `sqlite3BtreeIndexMoveto`) rejects depth >= `BTCURSOR_MAX_DEPTH`(20) levels, which is the only cycle protection, and rejects any child page with 0 cells or with an intKey flag different from the root's. Leaf-vs-interior consistency of children, uniform leaf depth, key ordering, overlapping cells, and pages referenced twice are not checked on read at all; they are `integrity_check`-only. `SQLITE_CORRUPT_PAGE(p)` is just `SQLITE_CORRUPT_PGNO(p->pgno)` (logs the page number); every such check surfaces as `SQLITE_CORRUPT`.

## 3. Most important gaps

SQLite rejects, we accept:
1. **PAGE-21**: a child page with 0 cells (leaf or interior) is always CORRUPT in SQLite; we read it as empty.
2. **PAGE-18**: page 1 (sqlite_master) with an index page type is CORRUPT in SQLite at schema load; we read it as a WITHOUT ROWID tree. For user tables the kind/SQL mismatch is checked only by the Sql package's `GetTableDefinition()`, not by `EnumerateRows()`.
3. **PAGE-19**: an interior root with 0 cells that is not page 1 is CORRUPT in SQLite; we follow its right-most pointer.
4. **PAGE-03**: `nCell > (pageSize-8)/6` is CORRUPT in SQLite; our bound is "pointer array fits in the page", about 3x looser.
5. **PAGE-14**: our page-count limit is `max(file pages, header size)`; SQLite uses the header size when valid (else file size), so pointers between the header size and the file size are CORRUPT in SQLite and accepted by us.

We reject, SQLite accepts (Lenient candidates):
1. **PAGE-11/12**: cell-pointer range and cell-extends-past-usable-area checks; SQLite does these only with `cell_size_check=ON`. We also run them for every cell when the page is loaded, so one bad cell fails the whole page (and earlier rows on that page are not returned), while SQLite fails only when it reaches that cell, and only if the payload read itself goes out of bounds.
2. **PAGE-17**: a 0-byte file is an empty database in SQLite; we report "file length" corruption.
3. **PAGE-14**: a partial trailing page is counted and zero-filled by SQLite; we treat it as truncation.
4. **PAGE-13**: we decode interior table keys on a scan; SQLite never does, so a malformed key at the very end of an interior page fails only for us.
